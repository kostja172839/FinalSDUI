# Split Studio

Конструктор SDUI Split-view для аналитиков: карточка собирается из смысловых блоков, значения задаются явно или берутся из любого пути в ответе API, а backend хранит и разрешает определение. Каталог содержит подсказки. Предпросмотр и приложение используют один renderer на SDDS FinAI.

В верхней навигации доступен отдельный **JSON-редактор** данных и схемы с предпросмотром и переходом к ошибкам. Новые примеры используют нейтральные `entity` и `collections`; старые определения совместимы. Добавлены сообщения, суммы с пояснениями, карточки связанных сущностей, документы и реквизиты в шапке. См. [JSON и валидация](docs/JSON-EDITOR.md).

Для обычной работы переходить в JSON не требуется: значение по привязке можно создать или изменить в свойствах поля. Кнопка **«Данные и шаблон»** прямо над сплитом показывает оба редактора одновременно; визуальные изменения обновляют общий шаблон. Неприменённый JSON защищён от перезаписи более новыми правками.

Блоки можно перетаскивать за ручку в дереве или прямо в карточке: менять порядок, переносить между вкладками и разделами, добавлять из палитры. Клавиатура: Space начинает перенос, стрелки выбирают место, Space / Enter завершают, Escape отменяет. Есть кнопки изменения порядка и выбор контейнера. Ctrl/Cmd+Z отменяет изменение конструктора, Ctrl+Y / Cmd+Shift+Z повторяет; в текстовых и JSON-полях работают собственные команды редактора. Выбор отдельного поля в карточке открывает его настройки, включая поля вложенных разделов, шапки, показателей и записей.

Для просмотра добавлены настоящие FinAI Badge, Avatar, Image, Progress и Divider. В палитре есть **ERP-таблица**: для неё подготовлены настройки SDUI, адаптер и данные по предоставленным контрактам. Приватный `ErpTableWidget` по умолчанию не подключён; блок показывает состояние подключения. Настоящий компонент из `@sber-sbererp/sdds-kit` передаётся через `App.erpTableAdapter` либо `SplitView.erpTableAdapter` и сам загружает метаданные и строки. Состав новых блоков задаёт `Catalog.authoringNodeTypes`.

Данные можно проверить независимо от UI: `GET /api/demo/erp-table/expenses/metadata` и `POST /api/demo/erp-table/expenses` принимают присланную форму `sorts` / `filters` / `pageable`. Фильтр `reportId = demo-report-001` возвращает 8 из 16 синтетических расходов. Также подготовлен источник `/api/demo/erp-table/product-events`. Кнопка **«Пример: расходы по отчёту»** в конструкторе настраивает блок; таблица появится после подключения настоящего компонента. JSON запроса, PowerShell-проверка API и пример интеграции — в [ERP-TABLE.md](docs/ERP-TABLE.md).

Устаревшие блоки `table` в сохранённых шаблонах читаются как JSON и показывают подсказку о замене на `erpTable`. Таблица из FinAI в сплите больше не отображается. Сохранённые черновики и опубликованные версии автоматически не переписываются.

Первая версия предназначена для **просмотра данных**. В неё входят заголовок и статус, вкладки, группы реквизитов, сворачиваемые разделы, описание, ссылки, таблицы и интеграционный контракт виджетов. Редактирование бизнес-полей, формы и комментарии оставлены для следующего этапа.

В шапке сплита есть меню с троеточием, в закреплённой нижней панели — меню «Действия» и отдельные кнопки. Выберите **Нижняя панель → Добавить кнопку**, задайте подпись, стиль и действие: обработчик приложения с параметрами, внешний виджет, обновление или закрытие сплита. Меню настраивается независимо. Подробности и подключение обработчиков — в [контракте действий](docs/ACTIONS.md).

## Запуск

Нужны Node.js 22+ и pnpm 10.26+ либо pnpm 11. Для проверки проекта используется Node.js 24. Команды выполняются из каталога проекта.

```sh
pnpm install
pnpm dev
```

Откройте [Split Studio](http://127.0.0.1:5173). Vite работает на порту `5173`, Node.js API — на `4310`; запросы `/api` проксируются автоматически. Порты должны быть свободны.

Первое открытие создаёт локальный файл `server/data/templates.json` с демонстрационными шаблонами. Сохранённые черновики и публикации остаются в этом файле после перезапуска. Другой каталог можно задать переменной `SDUI_DATA_DIR`.

## Как попробовать

1. Выберите шаблон «Основное средство» или «Нематериальный актив».
2. В конструкторе выберите заголовок, вкладку или блок в структуре слева. Настройте его свойства и источники данных справа.
3. Добавьте группу реквизитов, описание, сворачиваемый раздел, таблицу или зарегистрированный виджет. Источники выбираются по понятным названиям; вручную писать JSON не требуется.
4. Нажмите «Данные» в верхней панели и переключите сущность и сценарии: обычные, длинные или пустые значения, ошибка источника. Там же можно проверить ширину `600` и `840` px либо адаптивный режим. Сам сплит занимает всю доступную высоту рабочей области.
5. Исправьте ошибки, сохраните черновик и нажмите «Опубликовать».
6. Перейдите в «Приложение» и откройте объект из таблицы. Здесь используется активная опубликованная ревизия, а не несохранённый черновик.
7. В «Версиях» переключите активную публикацию. Это меняет карточку приложения и сохраняет текущий черновик аналитика.

Есть отмена/повтор изменений в текущей сессии и экспорт определения в JSON. Экспорт полезен разработчикам и для переноса примера; он не является обязательной частью работы аналитика.

## Два исходных сценария

| Шаблон               | Что показывает                                                                                                                                                 |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Основное средство    | Карточка оборудования: общие сведения, договор, идентификация и расположение; учётная стоимость; продуктовые события. Пример — «Банкомат офисный SelfServ 22». |
| Нематериальный актив | Та же архитектура для другого состава реквизитов: исключительные права, партия и вид ТМЦ; стоимость и события. Пример — персонаж «Лесной друг».                |

Данные примеров синтетические. Оба готовых шаблона используют `entityType: "asset"`; собственные типы сущностей и ответы API подключаются через `ServerOptions.loadEntity`, `listEntities` и `catalog`. В конструкторе доступны произвольные пути, заданные значения и собственный JSON для предпросмотра. См. [Источники данных](docs/DATA-SOURCES.md).

## Предпросмотр и приложение

Предпросмотр отправляет на backend текущий черновик, включая несохранённые настройки. Backend проверяет его и возвращает `ResolvedSplit` с определением, данными и локальными ошибками блоков. Проверочные сценарии меняют только демонстрационный снимок данных.

Приложение запрашивает сохранённую активную публикацию. Публикация создаёт неизменяемый снимок определения; последующее редактирование черновика этот снимок не меняет. При конкурирующем сохранении backend проверяет `expectedDraftVersion` и возвращает конфликт вместо перезаписи чужого черновика.

Пользовательские состояния чтения — выбранная вкладка, раскрытие, ширина и fullscreen — остаются на клиенте. Для `erpTable` загрузкой строк, поиском, сортировкой и страницами управляет подключённый `ErpTableWidget`.

## Виджеты

Встроенный `asset-history` демонстрирует `mount / update / unmount` адаптера с контекстом сущности. Реестр находится в `src/runtime/widgets.ts`. В определение попадает только известный `widgetId`; адреса загрузки JavaScript и исполняемый код аналитик не задаёт.

Для интеграции по вашим примерам добавлен `createSberERPWidgetAdapter`: хост передаёт настоящий `SberERPConnector`, а SDUI задаёт параметры `data` и события, включая `onClose`, `setOpened` и `buttons.accept.handler`. Доступны встроенные блоки и отдельный запуск из действий. Три локальных примера показывают передачу параметров, без загрузки внутренних микрофронтов. См. [Подключение SberERPConnector](docs/MICROFRONTENDS.md).

Для отдельного виджета host получает событие `sdui:open-widget` с `OpenWidgetIntent` и возвращает `sdui:widget-result` с `WidgetResult`. Ответ проверяется по `correlationId`, сущности и экземпляру сплита. `completed` с `dataChanged: true` запускает обновление данных.

Панель проверки интеграции в приложении имитирует ответ host и не меняет бизнес-данные. Реальный микрофронтенд, его loader и корпоративная авторизация в демонстрации не подключены. Подробнее — [контракт виджетов](docs/WIDGETS.md).

## Сборка и проверки

```sh
pnpm typecheck
pnpm test
pnpm build
```

После сборки можно запустить интерфейс и API одним Node.js-процессом:

```sh
pnpm start
```

Откройте [собранное приложение](http://127.0.0.1:4310). `start` использует `dist/`, поэтому сначала нужен `build`. Это локальная проверка production-сборки, не настройка внешнего развертывания.

## Структура

```text
shared/
  model.ts          Типы определения, экземпляра и виджетов
  catalog.ts        Подсказки полей и зарегистрированные виджеты примеров
  validation.ts     Общая структурная и семантическая проверка
  seeds.ts          Демонстрационные шаблоны и сущности
server/
  app.ts            HTTP API и раздача production-сборки
  store.ts          Локальный файловый репозиторий шаблонов
  resolve.ts        Проверка и разрешение карточки с данными
src/
  App.tsx           Рабочее пространство и bridge виджетов
  builder/          Структура карточки и редактор свойств
  runtime/          Общий renderer, bindings и реестр виджетов
  widgets/          Демонстрационный встроенный адаптер
  ui.tsx            Адаптеры компонентов FinAI
tests/              Проверки контракта и HTTP API
docs/               Архитектура и интеграционные контракты
```

## Подключение к вашей системе

Проект запускается локально и не содержит корпоративной авторизации. Для внедрения нужно заменить синтетические данные адаптерами ваших API, связать каталог с реальной моделью и правами, а `TemplateStore` — с подходящим production-репозиторием. Loader и адаптеры ваших виджетов подключаются на стороне host.

Ближайшие шаги: проверить сценарии аналитиков на реальных карточках; подключить источники данных и права; добавить серверную загрузку больших таблиц; затем отдельно спроектировать формы с валидацией и конфликтами сохранения и блок комментариев. Эти возможности не реализованы в текущем этапе.
