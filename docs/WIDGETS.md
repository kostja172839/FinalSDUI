# Виджеты и хостовый контракт

Пользователь уточнил, что отдельные микрофронтенды в этой задаче — виджеты. В SDUI-модели сохраняется только зарегистрированный `widgetId`. Технология сборки и доставки микрофронтенда остаётся ответственностью приложения-хоста.

В прототипе есть демонстрация этого контракта. Она не является развернутым enterprise-микрофронтендом и не доказывает интеграцию с корпоративным loader, маршрутизацией, SSO или системой прав.

## Два способа использования

| Способ | Как задаётся | Кто управляет |
| --- | --- | --- |
| Встроенный | `ContentNode` с `type: "widget"`, `widgetId` и высотой | Widget host монтирует адаптер в контейнер блока. |
| Внешний | Действие футера со ссылкой на `widgetId`; создаётся `OpenWidgetIntent` | Приложение-хост решает, где и как открыть отдельный виджет. |

`WidgetDescriptor` в каталоге описывает ID, название, назначение, версию и режим `embedded`/`external`. Доступность виджета в редакторе и совместимость режима должны проверяться по реестру.

Определение шаблона не содержит import URL, адрес удалённого JavaScript, JSX или функцию обработчика. Дополнение реестра — управляемое изменение host-приложения.

## Контекст

```ts
interface WidgetContext {
  entityId: string;
  entityType: string;
  instanceId: string;
  locale: string;
}
```

`instanceId` различает два открытия одного и того же объекта. `entityId` и `entityType` задают бизнес-контекст. Контекст не является токеном доступа: реальный виджет и его backend обязаны проверять права самостоятельно.

В текущем интерфейсе нет бизнес-версии сущности, tenant ID и permission scope. Если реальная интеграция их требует, интерфейс следует расширить явно, а не добавлять произвольные секреты в SDUI-определение.

## Жизненный цикл встроенного адаптера

```ts
interface WidgetMount {
  update?: (context: WidgetContext, input?: WidgetInput) => void;
  unmount: () => void;
}

interface WidgetAdapter {
  mount: (
    container: HTMLElement,
    context: WidgetContext,
    emit: (event: WidgetRuntimeEvent) => void,
    input?: WidgetInput,
  ) => WidgetMount | Promise<WidgetMount>;
}
```

Правила host-реализации:

`WidgetInput` содержит разрешённые параметры `data` и декларации `events`. `WidgetRuntimeEvent` поддерживает `dataChanged`, `close`, `host` и `error`. Готовый адаптер `name/data`, вложенные callbacks и отдельное открытие описаны в [MICROFRONTENDS.md](MICROFRONTENDS.md).

1. Найти адаптер по `widgetId` в доверенном реестре. Отсутствующий адаптер отображать как локальную ошибку блока.
2. Создать отдельный дочерний `mountRoot` для текущего поколения и вызвать `mount` с актуальным контекстом. До вызова проверить, что поколение ещё активно.
3. На смену контекста текущий runtime завершает предыдущий mount и создаёт новый. Необязательный `update` предусмотрен интерфейсом адаптера, но оптимизация через него пока не используется.
4. На удаление блока, смену адаптера или закрытие сплита вызвать `unmount`. Адаптер освобождает DOM, подписки, таймеры и обработчики.
5. Учитывать асинхронный `mount`: при cleanup `mountRoot` сразу отсоединяется от DOM. Поздно разрешившийся `WidgetMount` немедленно очищается через `unmount` и не получает контейнер нового поколения.
6. При обработке событий проверять актуальность контекста и поколения mount. Событие от старого экземпляра не должно обновлять другую сущность. Ошибка, отправленная адаптером во время `mount`, сохраняется: успешное возвращение `WidgetMount` не переключает такой блок в `ready`.

`update` в текущем типе синхронный. Для асинхронного обновления потребуется согласованный контракт отмены или новый mount; обещать поддержку `Promise` для `update` этот интерфейс не позволяет.

## Открытие отдельного виджета

```ts
interface OpenWidgetIntent {
  type: "openWidget";
  widgetId: string;
  context: WidgetContext;
  correlationId: string;
}

interface WidgetResult {
  correlationId: string;
  status: "completed" | "cancelled";
  dataChanged?: boolean;
}
```

Последовательность:

1. Renderer сообщает намерение открыть известный виджет.
2. Host создаёт/сохраняет связь `correlationId → instanceId + entityId + widgetId` и открывает виджет своим способом.
3. Host получает `WidgetResult` и проверяет, относится ли он к ожидающему вызову и актуальному экземпляру.
4. При `completed` и `dataChanged: true` запрашиваются свежие данные текущего сплита.
5. `cancelled` завершает ожидание без обновления данных.

Неизвестный или уже обработанный `correlationId` не применяется повторно. Результат для закрытого сплита не открывает панель заново и не обновляет другую сущность. Новое разрешение данных не должно произвольно сбрасывать активную вкладку и раскрытые разделы.

### События демонстрационного host

В `src/App.tsx` используется `CustomEvent` в текущем окне:

```ts
window.addEventListener("sdui:open-widget", (event) => {
  const intent = (event as CustomEvent<OpenWidgetIntent>).detail;
  // Host открывает зарегистрированный микрофронтенд своим способом.
  // После его завершения отправляет ответ с тем же correlationId:
  window.dispatchEvent(new CustomEvent<WidgetResult>("sdui:widget-result", {
    detail: {
      correlationId: intent.correlationId,
      status: "completed",
      dataChanged: false,
    },
  }));
});
```

Пример показывает форму обмена; реальный loader в нём нужно заменить своим. Прототип хранит один ожидающий внешний вызов: новое открытие заменяет предыдущий. При переходе между режимами рабочего пространства ожидание очищается. При обновлении данных для того же шаблона, ревизии и сущности `App` сохраняет `instanceId` текущего открытия.

Панель «Проверка интеграции» имитирует `completed`, `cancelled` и сообщение `dataChanged`. Она не выполняет реальную бизнес-операцию и не подключает внешний микрофронтенд. События текущего окна также не являются готовым протоколом для iframe или другого origin.

## Что означает read-only phase one

Сам SDUI renderer не редактирует поля сущности и не выполняет бизнес-команды. Отдельный виджет может владеть своим сценарием и сообщить, что данные изменились. Внутренности такого сценария не описываются деревом SDUI.

Для production-интеграции дополнительно понадобятся согласованные правила происхождения сообщений при iframe/postMessage, авторизация, ошибки запуска и таймауты, совместимость версий адаптера, аудит бизнес-операций и реализация реального loader. Наличие типов в `shared/model.ts` не означает, что эти внешние системы уже подключены.
