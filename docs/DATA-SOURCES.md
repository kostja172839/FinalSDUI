# Произвольные данные и значения

Каталог полей — подсказки для аналитика, а не список допустимых значений. В `ResolvedSplit.data` бэкенд может передать любой JSON-объект. Тип объекта `entityType` также не ограничен активами.

Нейтральная структура примеров: `entity` содержит данные текущего объекта, а `collections` — связанные списки. Например:

```json
{
  "entity": { "title": "Договор № 47", "status": "Зарегистрирован", "amount": 10000 },
  "collections": { "documents": [{ "name": "Договор.pdf", "href": "/documents/47" }] }
}
```

`asset` было названием данных первого примера с активами. Оно не является частью обязательного протокола. Старые определения с `asset.*` и `events` продолжают читать `entity.*` и `collections.events`; явный старый ключ в ответе API имеет приоритет. Обратная совместимость работает и для старых ответов API. Опубликованные определения не перезаписываются. `canonicalizeDefinition` даёт отдельную проекцию черновика с новым неймингом; пользователь сохраняет её обычным действием.

У поля, описания или таблицы есть необязательный `source`. Он имеет приоритет над прежним `binding`. У шапки аналогичные настройки называются `titleSource`, `subtitleSource`, `statusSource`.

```json
{
  "id": "applicant-name",
  "label": "Заявитель",
  "binding": "",
  "source": { "kind": "binding", "path": "response.application.applicant.fullName" },
  "format": "person"
}
```

Чтобы задать значение явно, используйте `{ "kind": "literal", "value": "Любое значение" }`. Допустимы строки, числа, boolean, null, массивы и объекты JSON. `false`, `0` и `""` не заменяются значением из старого binding. Формат отображения выбирается независимо от каталога.

Пути используют точку, например `response.people.0.name`. В колонке таблицы путь вычисляется относительно строки. Выражения, скобочная запись и обращения к `__proto__`, `prototype`, `constructor` не поддерживаются. Значение никогда не исполняется как код.

## Источник бэкенда

Вместо демонстрационных объектов передайте свои функции при создании сервера:

```ts
const server = createServer({
  catalog: companyCatalog,
  listEntities: () => repository.listSummaries(),
  loadEntity: async (entityId, entityType) => {
    const entity = await repository.find(entityType, entityId);
    return entity ? { data: entity.payload, version: entity.version } : undefined;
  },
});
```

`loadEntity` используется и для чернового, и для опубликованного сплита. Версия объекта возвращается в `entityVersion`; отсутствие объекта даёт 404. В данных ожидается JSON-объект без функций и служебных свойств, глубина до 24 уровней. Каталог виджетов задаётся на сервере и должен соответствовать доверенному реестру адаптеров клиента. Каталог из клиентского запроса не может зарегистрировать новый микрофронт.

## Проверка своих данных

`POST /api/resolve` в режиме `draft` принимает необязательный `previewData`. Этот объект заменяет данные демонстрационного объекта для текущего предпросмотра, не сохраняется в шаблон и не меняет бизнес-данные. Можно использовать произвольный `entityId`, даже если его нет в демонстрационном реестре. Для `published` этот параметр запрещён: приложение получает данные только от своего backend provider.

```json
{
  "templateId": "fixed-asset",
  "entityId": "application-901",
  "mode": "draft",
  "previewData": {
    "response": { "application": { "applicant": { "fullName": "Дарья Викторовна" } } }
  }
}
```

## Параметры микрофронтов

`props` у встроенного блока или действия — именованные `ValueSource`. Источники вычисляются относительно данных сплита. Дополнительно доступен `$context` с `entityId`, `entityType`, `instanceId`, `locale`. Например:

```json
{
  "props": {
    "flowId": { "kind": "binding", "path": "$context.entityId" },
    "file": { "kind": "binding", "path": "response.document" },
    "buttons.cancel.label": { "kind": "literal", "value": "Закрыть" }
  },
  "events": {
    "onClose": { "type": "close" },
    "onChange": { "type": "refresh" },
    "buttons.accept.handler": { "type": "host", "name": "printDocument" }
  }
}
```

Имена параметров через точку преобразуются в вложенный объект `WidgetInput.data`. Параметры и обработчики не должны перекрывать один и тот же путь. Функции событий создаёт адаптер на фронтенде. `host` ссылается на обработчик, зарегистрированный хост-приложением; JavaScript в JSON передать нельзя. Данные параметров копируются, поэтому виджет не изменяет исходный ответ сплита.

## Проверка значений каждого поля

У реквизитов, колонок таблиц, показателей, карточек списка и полей шапки есть необязательная настройка `validation`:

```json
{
  "id": "contract-amount",
  "label": "Сумма договора",
  "binding": "entity.amount",
  "format": "money",
  "validation": { "required": true, "min": 0, "max": 100000000 }
}
```

`required` проверяет заполненность; `minLength` и `maxLength` — длину текста; `min` и `max` — числовые границы для числа и суммы. Пустые необязательные поля допустимы. `0` и `false` считаются заполненными. Форматы дополнительно проверяют существующую календарную дату, конечные числа, текстовый статус/пользователя и безопасный адрес ссылки.

Ошибочные правила и заданные значения выявляются общей проверкой схемы до публикации. `validateResolvedData` отдельно проверяет текущие данные и возвращает конкретные `nodeId`, `fieldId`, `itemIndex`, путь настройки `path` и путь данных `dataPath`. Ошибка одной строки не мешает остальной карточке. Внешний backend остаётся владельцем окончательной бизнес-валидации и сохранения; данный этап отображает и проверяет данные просмотра.

## Новые блоки по макетам

- `callout`: информационные сообщения с типом info/success/warning/error.
- `metrics`: показатели и суммы с пояснением, например «с НДС».
- `recordList`: связанные карточки контрагентов или других сущностей с заголовком, описанием, ссылкой и реквизитами.
- `documents`: документы и связи с метаданными, статусом, размером и открытием зарегистрированного виджета. Для `action.props` текущий элемент доступен как `$item`.
- `header.fields`: закреплённые реквизиты под заголовком сплита.

В `recordList` и `documents` настройки `itemTitle`, `itemSubtitle`, `itemHref` и другие item-поля вычисляются относительно элемента списка. Колонки таблицы и поля карточки списка также читаются относительно строки. Пример договора экспортируется как `contractExampleDefinition` и `contractExampleData`; он не вставляется автоматически в существующее хранилище шаблонов.
