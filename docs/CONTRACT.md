# Контракт SDUI v1

Нормативные TypeScript-типы находятся в [shared/model.ts](../shared/model.ts). Этот документ объясняет их смысл. Поля ниже — интерфейс Split Studio; их нельзя считать одноимёнными React props SDDS FinAI.

## Определение карточки

`SplitTemplate` содержит:

| Поле            | Смысл                                                                                                    |
| --------------- | -------------------------------------------------------------------------------------------------------- |
| `schemaVersion` | Версия формата протокола; сейчас литерал `1`.                                                            |
| `id`, `name`    | Стабильный ID шаблона и имя для аналитика.                                                               |
| `entityType`    | Непустой тип бизнес-сущности; примеры используют `asset`, провайдер хоста может обслуживать другие типы. |
| `header`        | Bindings заголовка, подзаголовка и статуса; настройка видимости статуса.                                 |
| `shell`         | Исходная и минимальная ширина, максимальная доля ширины контейнера.                                      |
| `tabs`          | Упорядоченные вкладки с деревом поддерживаемых блоков.                                                   |
| `footer`        | Видимость, текст и необязательная ссылка на внешний виджет с подписью действия.                          |

Определение содержит пути к данным API или заданные значения. Необязательный `source` выбирает `{ kind: 'binding', path }` либо `{ kind: 'literal', value }` и имеет приоритет над прежним `binding`. Каталог содержит подсказки и не ограничивает пути. Путь читается через точку без выполнения выражений. Подробнее: [Источники данных](DATA-SOURCES.md).

## Семантические блоки

Все `ContentNode` имеют стабильные `id`, `title` и необязательное `visibleWhen`.

| `type`     | Назначение                                        | Настройки                                                                                  |
| ---------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `fields`   | Группа подписей и значений                        | 1, 2 или 3 колонки; `FieldDefinition[]`.                                                   |
| `section`  | Логический раздел с дочерними блоками             | `collapsible`, `defaultOpen`, `children`.                                                  |
| `text`     | Текстовое содержимое из данных                    | `binding`, возможность сворачивания.                                                       |
| `table`    | Связанные записи из снимка данных                 | Binding набора данных, выбранные колонки, поиск, размер страницы.                          |
| `erpTable` | Приватный `ErpTableWidget` хоста                  | `tableUrl`, высота, JSON-настройки и декларативные события; загрузку выполняет сам виджет. |
| `badge`    | Статус на FinAI Badge                             | `value`, семантический `tone`.                                                             |
| `avatar`   | Пользователь или организация                      | `name`, необязательный `src`, размер `s` / `m` / `l`.                                      |
| `image`    | Изображение                                       | `src`, `alt`, высота и `fit`.                                                              |
| `progress` | Прогресс                                          | `value`, положительный `max`, `showValue`.                                                 |
| `divider`  | Разделитель                                       | Необязательная подпись `label`.                                                            |
| `widget`   | Место для зарегистрированного встроенного виджета | `widgetId`, высота области.                                                                |

`FieldDefinition` задаёт ID, подпись, binding и один из форматов: `text`, `date`, `money`, `number`, `status`, `person`, `link`. Формат отвечает за отображение. Выбор формата не преобразует исходное поле в другой бизнес-тип.

В новых блоках значения задаются через `ValueSource`: произвольный безопасный путь API или JSON-литерал. `erpTable` использует отдельный контракт адаптера из [ERP-TABLE.md](ERP-TABLE.md), без запросов metadata/rows со стороны SDUI. Набор поддерживаемых типов сообщает `Catalog.nodeTypes`; необязательный `authoringNodeTypes` ограничивает только создание в палитре. Поэтому старый блок `table` можно продолжать читать, предлагая для новых схем `erpTable`.

Drag & Drop изменяет положение узла в `tabs[].nodes` / `section.children` или поля в совместимом контейнере, сохраняя ID и привязки. Поля шапки и обычных групп можно переносить между ними; поля повторяющегося списка — переставлять внутри своего списка, чтобы сохранить контекст строки. Показатели перемещаются между группами показателей. Схема проверяется на уникальность, циклы, максимум восемь уровней, 100 блоков в контейнере и 200 блоков в карточке. Выбор поля использует его собственный глобально уникальный ID.

`VisibilityRule` поддерживает только `equals` и `notEmpty`. `equals` сравнивает строковое представление значения с настроенной строкой. `notEmpty` считает отсутствующими `null`, `undefined` и пустую строку; ноль и `false` остаются заполненными значениями. Это небольшое декларативное условие по данным. В модели нет `eval`, функций, циклов, SQL или HTTP-произвольных выражений. Видимость интерфейса не является проверкой доступа.

Пустые значения форматируемых полей показаны как «Не указано», а текстовые bindings без значения — как `—`. Путь binding читается только по собственным полям объекта; сегменты `__proto__`, `prototype` и `constructor` запрещены. Ссылка представляется строковым адресом или объектом с `label` и `href`; адрес проходит проверку: допускаются относительные пути от `/` и протоколы HTTP/HTTPS. Произвольный `javascript:` URL не становится ссылкой. Список разрешённых внешних доменов в прототипе не реализован.

Адрес договора `/contracts/demo-041` в seed-данных иллюстрирует binding ссылки. Реальная карточка договора и её маршрутизация в проект не входят; для внедрения нужен маршрут вашего приложения или адаптер host-навигации.

## Четыре счётчика с разным смыслом

| Значение                                         | За что отвечает                                      |
| ------------------------------------------------ | ---------------------------------------------------- |
| `schemaVersion`                                  | Совместимость структуры SDUI-контракта.              |
| `draftVersion`                                   | Обнаружение конкурирующего редактирования черновика. |
| `PublishedVersion.revision` / `templateRevision` | Снимок опубликованного определения.                  |
| `entityVersion`                                  | Версия бизнес-данных, по которым разрешён экземпляр. |

`templateRevision: "draft"` означает предпросмотр черновика, а не публикацию с особым номером. Сохранение черновика не меняет активную публикацию. Номер ревизии шаблона не является версией UI kit.

`TemplateRecord` хранит черновик, его `draftVersion`, список `versions` и указатель `activeRevision`. Каждый элемент `PublishedVersion` содержит отдельный снимок `definition`. Публикации не должны ссылаться на изменяемый объект черновика в памяти.

## Разрешённый экземпляр

`ResolvedSplit` объединяет:

- `instanceId` для адресации конкретного открытия панели;
- `templateId` и `templateRevision` для воспроизводимого определения;
- `entityId` и `entityVersion` для контекста данных;
- `definition` — определение, которое действительно разрешено;
- `data` — разрешённые значения;
- `errors` — локальные ошибки `BlockError` с ID узла.

Renderer принимает этот объект и отображает его. Клиент не должен самостоятельно выводить бизнес-данные из состояния каталога или подменять определения разных ревизий.

## Каталог и проверка

`Catalog` содержит типизированные поля, наборы данных, зарегистрированные виджеты и типы блоков. Для аналитика каждое поле имеет понятную подпись, группу, описание и пример. Набор данных отдельно описывает доступные колонки.

Проверка возвращает `ValidationIssue[]`:

- `severity: "error"` — определение нельзя считать готовым к публикации;
- `severity: "warning"` — требуется внимание аналитика, например к читаемости;
- `path` — точное место настройки;
- `nodeId` — узел, к которому можно перейти в дереве;
- `message` — объяснение на языке пользователя.

Проверять требуется обе стороны: ограничения конструктора помогают пользователю, backend защищает контракт при прямом API-вызове. Проверки должны охватывать структуру, уникальность ID, допустимые bindings, типы данных и виджетов, диапазоны настройки оболочки и объём дерева.

Текущие ограничения `shared/validation.ts`:

| Настройка                | Ограничение                                                                          |
| ------------------------ | ------------------------------------------------------------------------------------ |
| Вкладки                  | От 1 до 12.                                                                          |
| Дерево                   | Не более 200 блоков и 8 уровней вложенности; до 100 элементов в одном списке блоков. |
| Группа полей             | От 1 до 50 полей; 1, 2 или 3 колонки.                                                |
| Таблица                  | От 1 до 20 колонок; целый размер страницы от 1 до 100.                               |
| Встроенный виджет        | Высота от 120 до 1200 px.                                                            |
| Минимальная ширина       | От 320 до 1600 px; значение меньше 600 px вызывает предупреждение по макетам.        |
| Исходная ширина          | Не меньше минимальной и не больше 2400 px.                                           |
| Максимальная доля ширины | От 30 до 100% контейнера.                                                            |

Три колонки и пустые вкладки/разделы вызывают предупреждения о читаемости и заполненности. Формат поля выбирается независимо от подсказки каталога. Режим виджета проверяется: встроенный блок принимает только `embedded`, действие меню — только `external`. Параметры `props` и декларации `events` доступны обоим видам виджетов; см. [Микрофронты](MICROFRONTENDS.md).

## Таблицы и снимки данных

`TableNode.pageSize` задаёт размер клиентской страницы. `binding` указывает на массив уже полученных записей. В phase one нет отдельного протокола серверного поиска, сортировки, cursor pagination или streaming.

При подключении больших production-таблиц нужно добавить контракт запроса: ID набора данных, фильтры, сортировку, страницу/курсор, версию запроса, состояние загрузки и ошибки. Простого увеличения числа записей в `data` для этого недостаточно.

## Совместимость

В v1 известен конечный набор блоков и форматов. Расширение реестра renderer требует соответствующей клиентской реализации. Неизвестный тип узла нельзя превратить в безопасный рабочий компонент одним изменением backend JSON.

`POST /api/resolve` принимает необязательные `capabilities.nodeTypes` и `capabilities.widgetIds`: списки строк. Если указанный набор не поддерживает блок или виджет определения, запрос возвращает ошибку проверки. Отсутствие capabilities означает проверку по общему каталогу прототипа. Автоматический fallback и миграции схемы не реализованы. Frontend и backend поставляются совместно и используют общий `shared/model.ts`.

## HTTP-интерфейс

Маршруты реализованы в [server/app.ts](../server/app.ts). Тела запросов и ответы — JSON. Для непустого тела требуется `Content-Type: application/json` (параметр `charset` допустим). Предел тела запроса составляет 1 МБ. API не использует cache ответов.

| Метод и путь                       | Вход                                   | Ответ                                                                                                                                    |
| ---------------------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/health`                  | —                                      | `{ status: "ok", mode: "read-only" }`; read-only относится к бизнес-данным.                                                              |
| `GET /api/catalog`                 | —                                      | `Catalog`.                                                                                                                               |
| `GET /api/entities`                | —                                      | Краткий список демонстрационных сущностей без их полного `data`.                                                                         |
| `GET /api/templates`               | —                                      | `TemplateRecord[]`.                                                                                                                      |
| `POST /api/templates`              | `{ name?, baseId? }`                   | Новый `TemplateRecord`, статус `201`. Копируется черновик `baseId`, по умолчанию — базовый seed-шаблон. Публикаций у новой карточки нет. |
| `GET /api/templates/:id`           | —                                      | `TemplateRecord`.                                                                                                                        |
| `PUT /api/templates/:id`           | `{ definition, expectedDraftVersion }` | Сохранённый `TemplateRecord` с увеличенным `draftVersion`.                                                                               |
| `POST /api/templates/:id/validate` | `{ definition? }`                      | `ValidationIssue[]`; по умолчанию проверяется сохранённый черновик. Наличие ошибок отражается в массиве при статусе `200`.               |
| `POST /api/templates/:id/publish`  | `{ expectedDraftVersion }`             | `TemplateRecord` с новым неизменяемым снимком и активированной ревизией.                                                                 |
| `POST /api/templates/:id/activate` | `{ revision }`                         | `TemplateRecord` с переключённым `activeRevision`. Черновик при этом не меняется.                                                        |
| `POST /api/resolve`                | См. ниже                               | `ResolvedSplit`.                                                                                                                         |

`/api/resolve` принимает:

```json
{
  "templateId": "fixed-asset",
  "entityId": "asset-001",
  "mode": "published",
  "scenario": "normal",
  "capabilities": {
    "nodeTypes": ["fields", "section", "text", "table", "widget"],
    "widgetIds": ["asset-history", "asset-editor"]
  }
}
```

ID в примере соответствуют исходным демонстрационным данным. Актуальные значения можно получить из `/api/templates` и `/api/entities`. `mode` обязателен и равен `draft` или `published`. `scenario` необязателен; доступны `normal`, `long`, `empty`, `error`.

В режиме `draft` можно передать `definition` с несохранёнными настройками для предпросмотра. Его ID должен совпадать с ID шаблона, а полная проверка должна пройти. В режиме `published` берётся только активная сохранённая публикация; подмена `definition` в запросе запрещена.

Сохранение черновика проверяет корневую структуру, но позволяет временные ошибки содержимого. Полная семантическая проверка выполняется отдельным вызовом, при публикации и при resolve. Опубликовать черновик с ошибками нельзя; предупреждения допустимы.

Основные коды ошибок: `400` — некорректный запрос, `404` — неизвестный шаблон/объект/ревизия, `409` — конфликт `expectedDraftVersion`, `413` — слишком большое тело, `415` — непустое тело без JSON Content-Type, `422` — недопустимое определение, `500` — внутренняя ошибка. Формат: `{ message, issues? }`.

Переключение активной ревизии в демонстрации не использует optimistic version check: при конкурирующих вызовах действует последний успешный запрос. Production-процесс публикации должен отдельно определить права, согласование и конкурентное переключение активной версии. Debug-сценарии `scenario` также следует вынести из production-пути данных.

Контракт виджетов и корреляция результатов описаны в [WIDGETS.md](./WIDGETS.md).
