# Кнопки и меню действий сплита

В конструкторе выберите **Нижняя панель → Кнопки в нижней панели → Добавить кнопку**. Задайте подпись, стиль и действие. Кнопка появляется непосредственно в закреплённом футере. Меню настраивается отдельно ниже.

## Отдельные кнопки

`footer.buttons` — необязательный список до шести кнопок. Их ID уникальны во всём шаблоне. `variant` принимает `primary`, `secondary` (по умолчанию), `ghost` или `danger`. Рекомендуется одна акцентная кнопка.

```json
{
  "show": true,
  "text": "",
  "actions": [],
  "buttons": [
    {
      "id": "approve",
      "label": "Согласовать",
      "variant": "primary",
      "action": {
        "kind": "host",
        "actionId": "request.approve",
        "params": {
          "requestId": { "kind": "binding", "path": "$context.entityId" },
          "decision": { "kind": "literal", "value": "approved" }
        }
      }
    }
  ]
}
```

Это пример содержимого `footer`. Доступны четыре вида `action`:

| kind         | Поведение                                            | Настройки                     |
| ------------ | ---------------------------------------------------- | ----------------------------- |
| `host`       | Вызвать зарегистрированный обработчик приложения     | `actionId`, `params`          |
| `openWidget` | Открыть внешний микрофронт через существующий bridge | `widgetId`, `props`, `events` |
| `refresh`    | Обновить карточку                                    | Без дополнительных настроек   |
| `close`      | Закрыть сплит                                        | Без дополнительных настроек   |

`params` поддерживает произвольные имена, вложенные пути через точку и источники `binding`/`literal`. Значения из `$context` берутся из текущего экземпляра сплита. Для `openWidget` действует тот же контракт параметров и событий, что у пунктов меню.

### Подключение действия продуктовой командой

1. Разработчик регистрирует описание в серверном `Catalog.actions`: `id`, `name`, `description`, при необходимости `inputs` с типами, обязательностью и значениями по умолчанию. Такой каталог передаётся в `createServer({ catalog })`.
2. В приложении подключает обработчик с тем же ID через `SplitView.actionHandlers`.
3. Аналитик выбирает его в конструкторе, называет кнопку и заполняет параметры. JSON-код обработчика не требуется.

```tsx
<SplitView
  document={resolved}
  actionDescriptors={catalog.actions}
  actionHandlers={{
    'request.approve': async ({ params, context, correlationId }) => {
      await requestsApi.approve({
        requestId: params.requestId,
        decision: params.decision,
        correlationId,
      });
      await refreshEntity(context.entityId);
    },
  }}
/>
```

API и проверку бизнес-правил реализует продуктовая команда в своём обработчике. Проверка прав и повторного исполнения остаётся на её сервере. `correlationId` позволяет связать нажатие с операцией. Библиотека ожидает Promise, блокирует повторные нажатия до завершения и показывает ошибку рядом с кнопкой. Смена карточки или настроек кнопки изолирует старые результаты. Неподключённый обработчик делает кнопку недоступной с пояснением.

Сервер проверяет зарегистрированное действие, источники и типы заданных параметров, обязательность, подпись, стиль и ограничения списка. Передавайте `actionDescriptors={catalog.actions}` в рендерер: обязательность и типы значений из binding проверяются перед вызовом, а проблема показывается возле кнопки. Без дескрипторов проверку параметров выполняет обработчик. Клиент может передать `capabilities.actionIds` наряду с `widgetIds` и `nodeTypes`; каталог из запроса клиента не заменяет доверенный серверный каталог. Бизнес-ограничения проверяет обработчик при выполнении.

В локальном приложении зарегистрировано `demo.inspectParams`: оно подтверждает получение текстового параметра `message` и не меняет бизнес-данные. Реальный `request.approve` из примера нужно зарегистрировать в своём приложении.

## Меню

В шапке используется кнопка с тремя точками, в закреплённой нижней панели — кнопка «Действия». Нижний список открывается вверх. Оба меню настраиваются в конструкторе при выборе шапки или нижней панели.

## Контракт

`header.actions` и `footer.actions` — независимые необязательные массивы до 12 пунктов:

```ts
type SplitAction = {
  id: string;
  label: string;
  kind: 'openWidget';
  widgetId: string;
};
```

ID пунктов уникальны в пределах определения. `widgetId` выбирается из каталога внешних виджетов. Клиент и сервер проверяют известный тип действия, подпись, целевой виджет и возможности клиента.

В первой версии действие передаёт хосту `OpenWidgetIntent` с контекстом объекта и новым `correlationId`. Само меню не выполняет операции над бизнес-данными. Результат виджета обрабатывается существующим bridge; `dataChanged` может обновить текущую карточку.

## Существующие шаблоны

Сохранённые определения, в которых есть только `footer.widgetId` и `footer.actionLabel`, продолжают работать. Функции `getHeaderActions` и `getFooterActions` выводят по одному пункту для каждого размещения, не меняя определение или опубликованную ревизию.

- Отсутствующее свойство `actions` включает это наследуемое поведение.
- Явный пустой массив `actions: []` скрывает соответствующее меню.
- Непустой массив полностью задаёт меню.

При первой настройке меню конструктор явно сохраняет оба списка и убирает устаревшие одиночные свойства. Это сохраняет второе размещение при изменении первого.

## Поведение клиента

`ActionMenu` получает пункты, контекст, размещение и callback `onOpenWidget`. Доступны переключение пунктов стрелками, Home/End, закрытие по Escape или нажатию вне списка. После Escape фокус возвращается на кнопку. При смене сущности, экземпляра или состава действий список закрывается. Если callback хоста не подключён, кнопка недоступна.

Кнопки используют адаптеры SDDS FinAI. Управляемый popup реализован в модуле приложения, чтобы согласовать его жизненный цикл с контекстом сплита. Это не отдельный промышленный микрофронтенд.
